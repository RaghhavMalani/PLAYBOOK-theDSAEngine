Module 01 // dynamic array

The memory engine

Python's list, C++'s vector and Java's ArrayList are the same machine: a contiguous block, a size, and a capacity. Push until capacity runs out and it silently allocates a bigger block and copies everything across. What differs between them is the growth factor — and it is not 2× everywhere, despite what most tutorials say. Switch models below and watch the spikes rearrange.

Keep pushing. The spikes get twice as tall but twice as rare — so the running average flatlines near a constant. That is what "amortised O(1)" means, and it is why nobody worries about append.

Say this in an interview: "Capacity grows geometrically, so the total copy work across n appends is a geometric series that sums to O(n) — amortised O(1) per append."

Then be specific, because the factor is not 2× everywhere. With growth factor g, the total elements copied over n appends is ≈ n / (g - 1) measured at the moment the array has just grown. So doubling costs ≈ n copies, 1.5× costs ≈ 2n, and CPython's ~1.125× costs ≈ 8n — eight times the memory traffic for the same result. All three are amortised O(1); only one of them is "less than 2n".

Run the three models above and read the elements copied counter — but read it carefully, because two things move it. First, where you stop matters: land exactly on a full array and doubling reads 1.00n; stop just after a reallocation and it reads nearly 2n, because you have paid for headroom you have not filled yet. That spread is precisely why the honest word is "amortised" and not "constant".

Second, CPython's 1.125× is asymptotic, not immediate. The real rule is newsize + newsize/8 + 6, and at small sizes that +6 dominates — 4→8 and 8→16 are outright doublings. So the effective factor starts near 1.25 and only decays toward 1.125 as the list grows. Click a few hundred pushes and you will read about 5n, not 8n; the 8n figure needs n in the tens of thousands. Quoting an asymptotic constant at small n is the same error as quoting O(n log n) for a 10-element sort.

The practical half: if you know the final size, pre-allocate — v.reserve(n) in C++, new ArrayList<>(n) in Java. Python has no equivalent. [0]*n sets the size to n, not the capacity — follow it with append and you end up with 2n elements. Pre-allocate and assign by index, or just append and accept the churn.
Module 02 // locality

The half Big-O can't see

Two loops touch the same n elements. Both are O(n). One runs eight times slower. Big-O counts operations; hardware charges you for cache misses, and those depend entirely on the order you touch memory. The CPU never fetches one value — it fetches a 64-byte line. Use all eight doubles in that line and seven of your reads are free. Use one and throw the rest away, and you pay full price eight times over.

Both traverse 64 elements. The vector's addresses are consecutive, so the hardware prefetcher sees the pattern and pulls the next line in before you ask — 8 line fetches, all overlapped.

The list can't be prefetched at all: you don't know where node i+1 lives until the load of node i completes. Every hop is a dependent load that stalls the pipeline. 64 nodes, 64 misses, none overlapped.

This is why std::list loses to std::vector even at insertion in the middle — the O(n) shift is a fast linear memcpy, while the O(1) splice needs an O(n) pointer-chase to reach the position.

Try this: run column-major at cache size 4 — 64 misses, 8× the memory traffic for identical work. Now drag cache size to 8. Same traversal, same code, 8 misses. Nothing changed except that the working set started fitting. That is the entire idea behind loop tiling: don't reorder the algorithm, shrink the block it works on until it fits in cache.

Say this in an interview: "Both are O(n·m), but the row-major version is cache-friendly — each 64-byte line is fully consumed before eviction. Column-major touches one element per line and evicts before reuse, so it pays a miss per element. Same complexity, different constant — usually 5–10× on real hardware." Then note the caveat: C and C++ are row-major, so iterate the last index fastest; Fortran and MATLAB are column-major, so the advice inverts.

Module 04 // recognition

Which pattern is this?

Knowing the five templates is the easy half. The hard half — the half that decides the interview — is looking at a paragraph of prose and knowing within thirty seconds which shape it is. That skill is a decision tree, not a memory feat. Walk it below, or open the full map and study the signals directly.

guided router
The meta-skill: read the constraints before the prose. n ≤ 10⁵ plus "contiguous" is almost always a sliding window or a prefix sum. n ≤ 10⁵ plus "minimise the maximum" is binary search on the answer, essentially every time. n ≤ 20 is bitmask. n ≤ 500 is O(n³) and the interviewer has already told you they'll accept it. The constraint block is the interviewer quietly handing you the intended complexity — most candidates skim straight past it.
